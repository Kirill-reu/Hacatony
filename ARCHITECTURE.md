# Архитектура

## Соответствие ТЗ

| ТЗ | Модуль |
|---|---|
| §2.1 Парсинг шаблона, токены дизайн-системы | `app/pipeline/template_parser.py` |
| §2.2 Генерация структуры и текста по брифу | `app/pipeline/content_generator.py` |
| §2.3 Графики/таблицы/диаграммы/пиктограммы, §2.3.1 изображения | `app/pipeline/visual_generator.py` + `slide_builder.py` |
| §2.4 Версионирование скиллов/агентов | промпты — строки-константы в `content_generator.py`/`visual_generator.py`; задел под вынос в отдельные конфиг-файлы см. README "Дальнейшие шаги" |

## Слои и границы

```
app/
  main.py              FastAPI: /templates, /generate, /jobs/{id}, /jobs/{id}/download/...
  config.py            Все настройки — из переменных окружения, с рабочими дефолтами
  schemas.py           Pydantic-модели HTTP API (не путать с внутренними dataclass-ами пайплайна)
  storage.py           Файлы на диске (data/) + in-memory реестр задач (JobStore)
  llm/
    text_client.py     LLM-клиент: любой OpenAI-совместимый /chat/completions + офлайн-заглушка
    image_client.py    text-to-image клиент: любой OpenAI-совместимый /images/generations + офлайн-заглушка
  pipeline/
    template_parser.py Декомпозиция .pptx: цвета темы, шрифты, типографическая шкала,
                        классификация макетов (title_slide/content_bullets/two_content/
                        comparison/content_image/section_header/title_only/blank/generic),
                        отступы, логотипы на мастер-слайде
    data_provider.py    Веб-поиск фактов для обоснования цифр (DuckDuckGo, без ключа API)
    content_generator.py Бриф + факты + доступные макеты -> SlidePlan (JSON от LLM,
                        с детерминированным rule-based фолбэком, если LLM недоступна
                        или вернула невалидный ответ)
    visual_generator.py Данные для графика/таблицы — строго из найденных фактов
                        (LLM-экстракция с проверкой на "выдумывание" чисел + regex-фолбэк),
                        промпт для картинки, нативная "SmartArt-like" icon-row из автофигур
    slide_builder.py    Сборка итоговой презентации на макетах ИЗ ШАБЛОНА пользователя:
                        текст — через runs (не text_frame.text=, чтобы не терять
                        форматирование), графики/таблицы/картинки — нативные объекты
                        на месте плейсхолдера
    audit.py             Детерминированный аудит (вёрстка/шаблон/плотность/целостность,
                        по чек-листу Приложения 1) + контекстный аудит (11 вопросов
                        да/нет через LLM)
    exporters.py         .pptx (Presentation.save), .pdf (LibreOffice headless,
                        опционально), .html (собственный рендер: текст остаётся
                        текстом, таблицы — таблицами, картинки — data URI,
                        графики — PNG-снэпшот через matplotlib)
    variant_engine.py    Оркестрация 3 вариантов с бюджетом времени на всю задачу
```

Направление зависимостей — сверху вниз: `main.py` вызывает `variant_engine`,
тот — `content_generator` → `slide_builder` → `exporters`/`audit`. Ничего в
`pipeline/` не импортирует `main.py` или `schemas.py` — внутренние
dataclass-ы (`SlidePlan`, `DesignSystem`, `AuditReport`, ...) сериализуются в
Pydantic-схемы API только в `main.py`, чтобы пайплайн можно было гонять и
тестировать (см. `tests/test_pipeline_integration.py`) без HTTP-слоя вообще.

## Три варианта верстки

Ось различий (обосновано согласно ТЗ §2.5): **плотность контента и стиль
формулировок** + **предпочитаемый способ визуализации**. Макеты берутся
только из макетов, реально присутствующих в шаблоне — шаблон никогда не
меняется и не дополняется:

1. **concise** — 1–3 коротких буллета (≤8 слов), тон "заголовок новости",
   предпочитает график/icon-row, преимущественно одноколоночные макеты.
2. **detailed** — до 6 буллетов (≤15 слов), повествовательный тон с
   пояснением контекста, предпочитает таблицы, активно использует
   двухколоночные/comparison-макеты, если они есть в шаблоне.
3. **visual** — средняя плотность, но упор на изображения и icon-row перед
   текстом; также предпочитает многоколоночные макеты, чтобы визуально
   отличаться от `concise` даже на одинаковом контенте.

Конкретные параметры — `VARIANT_DEFINITIONS` в `variant_engine.py`.

## Пайплайн одного варианта

1. `template_parser.parse_template` — один раз при загрузке шаблона
   (результат кешируется в памяти процесса, см. `main._design_systems`).
2. `data_provider.gather_facts` — веб-поиск по брифу (общий для всех 3
   вариантов, чтобы факты были одни и те же и различия были именно в
   подаче, а не в источниках).
3. `content_generator.generate_plan` — LLM (или фолбэк) строит `SlidePlan`
   с учётом параметров варианта; каждый слайд помечен ролью макета
   (`layout_role`), которая реально есть в шаблоне.
4. `slide_builder.build_variant_deck` — грузит **исходный** `.pptx`
   пользователя, удаляет из него только слайды (`<p:sldIdLst>`), оставляя
   мастера/макеты/тему как есть, и добавляет новые слайды через
   `add_slide(layout)` на этих макетах. Для каждого слайда: заголовок и
   буллеты — в существующие плейсхолдеры (через runs), запрошенная
   визуализация (`chart`/`table`/`image`/`icon_row`) — заменяет один из
   content-плейсхолдеров нативным объектом; пустые лишние плейсхолдеры
   удаляются, а не остаются пустыми (иначе их поймает аудит).
5. `exporters` — сохраняет `.pptx`, конвертирует в `.pdf` (если есть
   LibreOffice), рендерит `.html`.
6. `audit.run_full_audit` — прогоняет готовый `.pptx` через детерминированные
   проверки и (если LLM настроена) через контентные вопросы из Приложения 1.

## Асинхронность и бюджет времени

`POST /generate` возвращает `job_id` немедленно; сама генерация идёт в
фоновом потоке (`threading.Thread`, см. `main._run_job`) и пишет прогресс в
`JobStore`. `variant_engine.generate_variants` принимает `deadline_ts`
(`time.monotonic()` на весь запуск, не на один вариант) и останавливается
после уже завершённых вариантов, если до дедлайна осталось <5 секунд — job
получает статус `timed_out` с тем, что успело собраться, вместо падения.

## Почему in-memory JobStore, а не очередь/БД

Для однопроцессного демо на хакатоне отдельная очередь задач (Celery/RQ) и
БД для их состояния — оверинжиниринг, который создаёт саму по себе точку
отказа накануне защиты. `storage.JobStore` — единственное место, которое
знает о хранении задач; замена на Redis — это переписать один класс, не
трогая `main.py`/`variant_engine.py`.
