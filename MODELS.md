# Модели

Сервис не завязан на конкретную модель — оба клиента (`app/llm/text_client.py`,
`app/llm/image_client.py`) говорят с любым **OpenAI-совместимым** эндпоинтом
(`/chat/completions` и `/images/generations`). Ниже — что реально
используется по ролям, требования ТЗ к моделям и куда вписать конкретный
выбор перед сдачей.

## Требования ТЗ к моделям (§3)

- Только открытые веса, лицензия **Apache 2.0 / MIT**.
- LLM/VLM/text-to-image — **до 35B** параметров; на отборочном этапе
  генерация изображений (задача со звёздочкой, §2.3.1) — **до 20B**.
- Инференс на отборочном этапе — свой GPU или внешний API-провайдер (для
  моделей с открытыми весами до 35B).
- Команды из топ-10 получают ресурсы — модель Qwen (в ТЗ: "Qwen 3.8 27b") и
  обязаны использовать инференс VK.

## Текстовая модель (планирование структуры, контент, извлечение данных для графиков/таблиц, контентный аудит)

- **Роль в сервисе**: `content_generator.py` (структура + текст слайдов),
  `visual_generator.py` (извлечение чисел для графиков/таблиц — только из
  предоставленных фактов), `audit.py` (11 контентных вопросов Приложения 1).
- **Настройка**: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` в `.env`.
- **Целевая модель**: Qwen3 (инференс VK, ресурс отборочного этапа) —
  конкретный тег модели и HF-ссылку вписать сюда после выбора команды, напр.:
  `LLM_MODEL=qwen3-27b-instruct` — ССЫЛКА_НА_HUGGINGFACE.
- **Системные требования**: при self-hosted инференсе (vLLM/TGI) — GPU с
  объёмом памяти, достаточным под выбранный чекпоинт в нужной точности
  (для 27B в fp16/bf16 ориентировочно ~55 ГБ VRAM; в 4-bit-квантовании —
  заметно меньше). При использовании инференс-шлюза VK — соответствовать его
  собственным лимитам (RPS/таймауты), см. `LLM_TIMEOUT_SECONDS`.
- **Фолбэк без модели**: `OfflineStubClient` (`app/llm/text_client.py`) —
  детерминированный rule-based план из брифа, без сети и без LLM. Не замена
  качеству реальной модели, а гарантия того, что пайплайн не падает и
  end-to-end воспроизводим локально/в CI.

## Text-to-image модель (задача со звёздочкой §2.3.1)

- **Роль в сервисе**: `visual_generator.generate_image` /
  `slide_builder._replace_with_picture` — по промпту из заголовка/подсказки
  слайда генерирует иллюстрацию, которая вставляется как обычная растровая
  картинка (единственное место в пайплайне, где результат — растр, что и
  требует сама природа text-to-image).
- **Настройка**: `IMAGE_BASE_URL`, `IMAGE_API_KEY`, `IMAGE_MODEL` в `.env`.
- **Требование ТЗ**: открытые веса, Apache-2.0/MIT, **класс до 20B** на
  отборочном этапе. Кандидаты, удовлетворяющие лицензии и размеру (выбор и
  конкретная HF-ссылка — за командой, вписать после решения):
  - `IMAGE_MODEL=sdxl-base-1.0` — Stability AI SDXL Base 1.0 (~3.5B, Apache
    2.0) — ССЫЛКА_НА_HUGGINGFACE.
  - более новая открытая модель класса ≤20B, если появится доступ через
    инференс VK — вписать сюда.
- **Системные требования**: зависят от выбранной модели; SDXL-класс — от
  одной GPU с ~12–16 ГБ VRAM для инференса в разумное время (укладывается в
  общий бюджет генерации колоды, см. README "Бюджет времени").
- **Фолбэк без модели**: `PlaceholderImageClient` (`app/llm/image_client.py`)
  — детерминированная градиентная PNG-плашка с текстом промпта (Pillow, без
  сети). Позволяет прогнать весь пайплайн (включая вставку изображения в
  слайд и аудит) без реального text-to-image эндпоинта.

## Веб-поиск (обоснование фактов/цифр, не генеративная модель)

- **Роль в сервисе**: `data_provider.py` — находит факты по брифу, чтобы
  текстовая модель не "галлюцинировала" цифры (см. AUDIT.md, пункт "Все
  цифры и факты со слайда есть в исходных материалах").
- **Реализация**: DuckDuckGo (`duckduckgo_search`), без API-ключа. Не
  подпадает под ограничения ТЗ §3 (это не генеративная модель), но
  сознательно выбран максимально доступным, чтобы не блокировать демо
  отсутствием ключа стороннего поискового API.
- **Отключение**: `WEB_SEARCH_ENABLED=false` — генерация продолжает
  работать, просто без обоснования цифр из интернета (модель ограничена
  только текстом брифа).
